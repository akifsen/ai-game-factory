# Installed-wheel V0.7 CLI candidate review

## Result

The frozen candidate wheel completed two independent local vehicle workflows
through the installed CLI, using a private in-process fixture registry. Both
flows ran real Blender and Godot, produced all nine required camera views, and
passed the 29-file cold evidence check. Each workflow used three explicit,
named test reviewers for concept, source, and final visual approvals. All five
paid-operation tables remained empty.

This is a candidate acceptance result, not release approval. A source/wheel
parity audit after the test found later concurrent source edits. The installed
wheel is kept frozen at the tested bytes; it was not rebuilt over those edits.
A final release wheel must be rebuilt and its checks repeated after the
provider-character, cold-verifier, and profile work is stable.

## Acceptance runs

The command transcript for the second fresh project is
`.verification/wheel-local-cli-r1/run2-cli-transcript.jsonl`; it records each
separate `python -I installed_cli.py ...` process, arguments, return code,
stdout, and stderr. The private shim at
`.verification/wheel-local-cli-r1/installed_cli.py` only injects the packaged
`vehicle@1` document into that process's local assembly registry. It does not
modify the built-in V0.7 catalog, expose a profile-file option, or change the
installed wheel. A separate V0.7 catalog query still reported `vehicle` as
`UNSUPPORTED`.

Both fresh projects completed this sequence:

```text
gamefactory init
gamefactory assembly ingest --spec armored_vehicle_test.yml --source source.glb --package sources/vehicle-r00N --actor fixture-source-author --reason "Isolated installed wheel CLI acceptance fixture" --authoring-tool "fixture GLB generator" --authoring-tool-version 1 --source-front=-Z
gamefactory assembly verify --spec armored_vehicle_test.yml --package sources/vehicle-r00N --expected-provenance-sha256 <ingest result>
gamefactory assembly create --spec armored_vehicle_test.yml --package sources/vehicle-r00N --expected-provenance-sha256 <ingest result> --concept concept.png --concept-provenance concept-provenance.json --workflow-id installed-wheel-vehicle-rN
gamefactory approve <pending-id> --actor fixture-human-concept-reviewer-rN --comment "TEST FIXTURE ONLY: explicit concept review"
gamefactory resume installed-wheel-vehicle-rN
gamefactory approve <pending-id> --actor fixture-human-source-reviewer-rN --comment "TEST FIXTURE ONLY: explicit source review"
gamefactory resume installed-wheel-vehicle-rN
gamefactory approve <pending-id> --actor fixture-human-final-reviewer-rN --comment "TEST FIXTURE ONLY: explicit final review"
gamefactory resume installed-wheel-vehicle-rN
gamefactory assembly export installed-wheel-vehicle-rN
gamefactory assembly export installed-wheel-vehicle-rN
```

Every CLI command ran in a new Python process, so the workflow engine was
rehydrated from its stored pins each time. Both runs completed all eight
workflow tasks. Blender reported `SUCCESS`, geometry validation reported
`PASS`, Godot reported `PASS` with restoration verified, and the independent
packaged cold verifier reported `PASS` for 29 files. The two runs matched on
the selected semantic fields: task and approval outcomes, source and processed
GLB hashes, all nine runtime capture hashes, and cold verification. Workflow
IDs, execution IDs, timestamps, and manifest hashes were excluded from that
comparison. Results are in
`.verification/wheel-local-cli-r1/semantic-repeat-comparison.json`.

The evidence response sets `product_ready: true` for internal consistency of
the exported bundle. It also correctly reports that human identity, execution
origin, capture origin, and changes after export are not authenticated by the
self-contained bundle.

## Read-only revalidation and tampering

Two consecutive completed exports returned the same manifest hash and left the
database SHA-256 unchanged. A completed export also passed when invoked with
`python -I` from the external Codex visualization directory and an explicit
project path; the database hash stayed
`f891d39c7f1c54203a4a45447733cc80477abeb74d51c078926b4b945338efe2` before
and after.

The packaged cold verifier passed when run with `python -I` from that same
external working directory, using its absolute `site-packages` script path and
the exported bundle path. It verified 29 files with `status: PASS`.

Each completed-export drift probe returned a controlled failure. The database
file hash was unchanged during each CLI call, and the isolated fixture was
restored before the next probe:

| Fixture drift | Result |
|---|---|
| Current processed GLB bytes changed | Artifact content hash mismatch |
| Current runtime capture PNG changed | Cold verifier rejected the bundle file |
| Latest Blender process attempt marked `FAILED` | Revalidation required a successful latest process attempt |
| Approved concept reviewer actor changed | Persisted human receipt differed from the current approval |

Raw outcomes and per-case before/after database hashes are in
`.verification/wheel-local-cli-r1/tamper-probes.json`. The original clean
workflow passed again after all fixture mutations were restored.

## Limits

This establishes that the frozen wheel can run the candidate vehicle flow with
a private test profile on this Windows/Python 3.12.14/Blender 5.2.1/Godot
4.7.2 setup. It does not activate the public V0.7 vehicle profile, establish
artistic quality, prove Linux behavior, or establish parity with the current
source tree. Those checks belong to the final wheel after concurrent changes
are reviewed and stable.
