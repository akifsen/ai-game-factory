## Paid Request Snapshot

`paid-request-0.6.0` (`core/domain/paid_request.py`, [architecture](../architecture/paid-request-snapshot.md), ADR 0009). The snapshot contains:

- provider, operation, adapter identity and contract version;
- the binding: asset, revision, concept version and hash, specification hash, profile;
- every material request option, with unsent options recorded as explicit `"omit"`;
- cost estimate, reservation and unit.

It is resolved by a dedicated `PAID-REQUEST` task, stored as an artifact whose bytes are the canonical form (artifact hash = request hash), and recorded in `paid_request_snapshots`.

## Request Canonicalization

The canonical form uses sorted keys, compact separators and UTF-8, with no NaN or Infinity. It accepts a strict value model and rejects timestamps, absolute paths, credential-like keys and values the redactor would change. The fingerprint is the SHA-256 of the canonical bytes. Tests cover:

- stability across key orderings, with a golden hash;
- every material field changing the hash;
- timestamps and report paths being rejected;
- absolute paths (POSIX, drive, UNC) being rejected;
- credentials being rejected;
- a snapshot whose declared hash does not match its content being refused.

## Approval Binding

The paid task's parameters carry the snapshot content, its hash and the PASS readiness report hash, so the approval fingerprint binds them. `approvals.paid_request_snapshot_hash` stores the bound hash. The checkpoint shows **PAID GENERATION APPROVAL REQUIRED** with asset, revision, provider, operation, request snapshot, request SHA-256, estimated cost, reservation, policy ceiling, readiness and approval status.

## Dispatch Drift Protection

Before any intent claim or process launch, dispatch requires:

- parameters = active snapshot record = approval = artifact hash;
- `load_verified`;
- a binding that names the active concept version, asset, revision and specification (provider-agnostic).

The adapter builds its create arguments only from the snapshot through a pure function and refuses with `PAID_REQUEST_INCOMPATIBLE`; it never translates. For V0.6 intents `request_fingerprint = paid_request_snapshot_hash`.

In the flagship test, adapter defaults changed after approval (1k textures, PBR off, a different model type) and the exact approved 2k/PBR/smart-topology request was still sent once. An incompatible adapter gives 0 submissions, 0 intents and the reservation released. A tampered snapshot gives 0 submissions. On Meshy, a new submission without a snapshot is refused (`PAID_REQUEST_REQUIRED`).

## Secret Redactor

Ambient environment values need at least 8 characters and must not be common literals before they become global replacement tokens. Explicit request-scoped secrets (credential overrides and credential-flag values) keep exact redaction from 4 characters. Key-aware patterns still redact `API_KEY=…`, `password: …` and `Bearer …`. With `AUTH_FLAG=1`, `TOKEN_FLAG=0`, `OAUTH_FLAG=true`, `SECRET_ENABLED=false` and the real `CLAUDE_CODE_SDK_HAS_HOST_AUTH_REFRESH=1` set, UUIDs, SHA-256 digests, JSON task IDs and `abc123` pass through unchanged. Realistic long keys are redacted.

Before V0.6 the suite failed on this host because a CLI SHA-256 was corrupted to `f76fa45d8ca20[REDACTED]4b69…`. Every V0.6 suite run below had the hostile variable present.

## Structured Output Safety

`CommandResult.protocol_stdout` holds raw protocol text in memory only: `repr=False`, not in `to_dict`, never persisted. Meshy doctor, get_task, download and create parse it. Logs and evidence keep the sanitized `stdout`. A test proves that a task ID parses exactly even when the sanitized stdout is corrupted.

## Accounting Model

`cost_ledger` is append-only (triggers abort UPDATE and DELETE), with RESERVE, SETTLE, RELEASE and ADJUSTMENT entries. It is the **single** spend authority for the claim, the policy check, `status` and `inspect`. `executions.cost` is a legacy display mirror. See the [architecture](../architecture/accounting.md) and ADR 0010.

## Settlement

These cases are tested: reservation > actual, actual > reservation, equal, unknown actual (held), in-flight partial below the hold (held) and above it (top-up), UNCERTAIN (held), terminal FAILED with cost (settled), and pre-submission failure (released).

The reviewer found that a retry on an already-settled operation could stack a new hold. This is fixed: the claim now reserves only the top-up for an operation and nothing once it is settled, and a regression test covers it.

## Reconciliation CLI

`gamefactory accounting reconcile --workflow WF` is a dry run by default. `--apply` requires `--actor` and `--reason`, is transactional, writes an `ACCOUNTING_RECONCILED` audit event, and a second apply is a no-op. It refuses UNCERTAIN or unknown-actual operations. It releases a hold without an intent only for `asset_paid_generation`, where the intent is journaled before any provider contact, and only when no record shows contact; every other paid task type without an intent is reported as not eligible, manual evidence required (see [Reconcile safety follow-up](#reconcile-safety-follow-up-pr-2-review)). `accounting ledger` lists the entries.

The dry run writes no ledger entries, but the CLI opens the database through `_db()`, which applies pending migrations; it is not a read-only inspection of a live schema-6 database. See the [operator procedure](../architecture/accounting.md#operator-procedure-for-a-live-database).

Historical fixture (schema 6 → 7, reserved 20 / recorded 20 / actual 15): after migration spend is 20, the dry run proposes SETTLE 15 + RELEASE 20 (net −5), and after apply spend is 15. The execution row is not mutated.

On a **scratch copy** of the real pickup production DB the result is identical (20 → 15). The operator later applied the same reconciliation to the live production DB; see [Operator Reconciliation of the Live Production DB](#operator-reconciliation-of-the-live-production-db).

## Recovery Inspection

## Recovery Reclassification

`gamefactory recovery reclassify --execution E` is a dry run by default. `--apply --actor --reason` performs a compare-and-set of `retryable 0→1` plus a `RECOVERY_RECLASSIFIED` audit event. There is no `--force`.

- **Eligible:** the exact historical production shape (no pid, exit code or output; "Godot executable is required…"; `ENGINE_IMPORT_FAILED`; no stage or logs).
- **Refused:** launched process, runtime validation, asset validation, paid tasks, already retryable.

On the scratch production copy, the real row `EXEC-41c22667` classifies as `PRE_EXECUTION_TOOL_CONFIGURATION`. It is reported as not applicable only because it was already repaired and the task completed.

## Paid Recovery Safety

Recovery never resets intents and never marks paid tasks retryable. An uncertain submission cannot be retried or reclassified and its intent rows are unchanged (tested). A provider SUCCEEDED result with a downstream failure keeps the invocation count at 1 through retry (tested). Exactly-once regression coverage around the snapshot layer includes repeated resume, retry and crash recovery.

## Concept Versioning

`concept_versions` holds immutable versions, with one ACTIVE per revision and triggers protecting content. Legacy revisions read as version 1 in memory. For V0.6 workflows `CHANGES_REQUESTED` → BLOCKED `CONCEPT_REVISION_REQUIRED`, while `REJECTED` stays terminal and legacy graphs keep the V0.5 semantics. `gamefactory request-changes` records the decision. See the [architecture](../architecture/concept-versioning.md) and ADR 0012.

## Concept Replacement

`gamefactory asset concept replace` works as follows:

- v1 (CHANGES_REQUESTED) → v2: v1 and its approval are preserved, v2 has a new hash, a fresh PENDING approval is opened, and there are 0 intents.
- Approving v2 gives a snapshot bound to v2, readiness, the paid approval, one submission, final review, and a v2 evidence bundle that is **cold-verified**.
- Replacement after concept approval with the paid approval pending supersedes the old snapshot and readiness, and the old paid approval can no longer be approved.
- An old pending concept approval cannot be approved.
- Dry run changes nothing.

The command holds the workflow execution lock (reviewer finding, fixed).

## Paid Boundary

Replacement is refused, with nothing changed, when an intent exists, a paid approval is APPROVED, or the workflow uses the legacy graph. Dispatch refuses a snapshot for a superseded concept, which covers an interrupted replacement (tested).

## Known Limitations

1. Concept replacement is a guarded sequence, not one transaction. An interruption can require operator cleanup or a new revision; it cannot authorize a payment for the wrong concept.
2. For options recorded as `"omit"` the provider's server-side default applies. The factory records the omission, not the provider's value.
3. Query-only recovery still passes the policy budget evaluation. A project already over budget after an overage settlement may need a budget adjustment to download an already-paid result.
4. `accounting reconcile` does not take the workflow lock. It re-evaluates the plan and the project balance inside its `BEGIN IMMEDIATE` apply transaction and refuses with `RECONCILIATION_STATE_CHANGED` if the plan changed; live applies are still run with workflows stopped.
5. Pre-V0.6 workflows that never submitted cannot start a new Meshy submission (`PAID_REQUEST_REQUIRED`); allocate a new revision.
6. Deep workspace paths can exceed Windows `MAX_PATH` in Blender. This is environmental and pre-existing. Since V0.7.0 the Blender processor rejects over-limit paths before launching Blender, with an actionable message.

## Reconcile Safety Follow-up (PR #2 review)

Two P1 findings from the PR #2 review were fixed before v0.6.0:

1. **Wrong RELEASE for paid tasks without an intent.** The no-intent branch could propose `RELEASE` for any paid task with terminal attempts, including legacy `paid_generation` tasks that were really charged but never journal an intent. RELEASE without an intent is now limited to `asset_paid_generation` with no RUNNING or COMPLETED attempt, no external operation ID and no recorded invocation. All other cases report `manual_evidence_required`. The r002 path (terminal `SUCCEEDED` intent with a known actual) is unchanged.
2. **Stale audit totals under concurrency.** `spend_before`, `spend_after` and `net_change` were computed before the write transaction. The plan and the project balance are now read on the apply transaction's connection under `BEGIN IMMEDIATE`. The audit event and the result report the committed change, and a plan that differs from the preview (or from `--plan-hash`) is refused with `RECONCILIATION_STATE_CHANGED` without writing.

The regression tests are in `tests/integration/test_reconcile_safety.py`: a charged legacy task keeps its hold, a pre-contact asset crash is released, ambiguous submissions are refused, and a concurrent spend, a changed actual cost, a concurrent settlement and a stale plan hash are handled. Interleavings are driven by a transaction hook, with no sleeps. Against the previous code the behavioral cases fail (legacy task released, audit `spend_before` 20 instead of 27, changed actual cost applied silently). With the fix the full suite passes.

Reconciling the live production database is **not** a v0.6.0 release prerequisite. Before any live apply you need a backup, quiescence (all workflows stopped), provider cost evidence, and a current dry run narrowed to the target task.
