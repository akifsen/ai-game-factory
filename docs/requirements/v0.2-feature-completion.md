## 5. WORKFLOW TASARIMI

Küçük, sıralı bir pipeline oluştur:

Senaryo ve proje ön kontrolü
→ policy/approval değerlendirmesi
→ yönetilen çalışma kopyası
→ Godot import
→ Godot senaryosu
→ bağımsız çıktı doğrulaması
→ mevcut quality gate
→ COMPLETED veya gerekçeli başarısızlık.

Adımların task sınırlarını mevcut mimariye göre belirle.
Her küçük fonksiyonu ayrı task yapma.

Kritik gereksinimler:

- Import başarısızsa runtime başlamaz.
- Runtime başarısızsa başarı gate'i açılamaz.
- Validation başarısızsa workflow tamamlanamaz.
- Sonraki görevler başarısız önkoşulu atlayamaz.
- Başarısız süreçlerin logları da saklanır.

Log toplama yalnız başarılı görevlerden sonra çalışan bir adıma bağlı olmamalıdır.
Hata ve timeout durumlarında da mümkün olan süreç kanıtını kaydet.

## 6. SENARYO SÖZLEŞMESİ

Küçük ve sürümlü bir JSON senaryo şeması tanımla.

En azından şu kavramları kapsasın:

- schema_version
- scenario_id
- proje içindeki test scene referansı
- desteklenen sınırlı eylemler
- eylemlerin uygulanacağı tick
- toplam tick sınırı
- örnekleme noktaları
- wall-clock timeout
- Python tarafında değerlendirilecek beklentiler

Gerekliyse kontrollü seed alanı ekle.
Rastgelelik kullanılmıyorsa sırf alan doldurmak için kullanma.

Eylemler açık bir allowlist üzerinden çalışmalı.
Örneğin fixture için:

- apply_damage
- defeat_enemy
- advance_ticks
- capture_state

Bunlar genel amaçlı script çalıştırma komutları değildir.

Şunları ekleme:

- eval veya exec
- keyfi GDScript metni
- keyfi node method adı
- shell komutu
- keyfi dosya yazma yolu
- ağ çağrısı
- serbest biçimli expression engine

Sayısal sınırları, desteklenen alanları, veri tiplerini ve dosya boyutlarını doğrula.
Bilinmeyen schema version, action veya alanı açıklayıcı hata ile reddet.

Geçersiz senaryo, Godot başlatılmadan reddedilmelidir.

Tam senaryo sözleşmesini snapshot olarak sakla.
Runtime'a gönderilen yürütme isteği ile Python'da tutulan
beklenti/oracle bölümünü ayır.

Harness'a beklenen sonucu kopyalayıp çıktı üretme fırsatı verme.

## 7. GERÇEK VE KÜÇÜK GODOT FIXTURE

Küçük bir Godot fixture oluştur veya mevcut örneği dikkatle genişlet.

Fixture gerçek bir sahne yüklemeli ve gerçek node durumunu değiştirmelidir.

Örnek davranış:

- Başlangıç oyuncu canı: 100
- Başlangıç düşman sayısı: 3
- Başlangıç skor: 0
- Tick 30: oyuncuya 20 hasar
- Tick 60: bir düşmanı yen; skoru 100 artır
- Tick 90: oyuncuya 40 hasar

Beklenen final durum:

- player_hp: 40
- enemies_remaining: 2
- score: 100

Bu sayılar örnek tasarım kararıdır; uygulamada tutarlı biçimde kullan.

Hasar, düşman yenme ve skor davranışı fixture'ın gerçek oyun kodunda olsun.
Harness yalnız bu davranışı kontrollü biçimde tetiklesin ve sonucu okusun.

Şunlar kabul edilmez:

- GDScript'in hazır “PASS” JSON'u yazması.
- Python'un Godot çalışmamışken state üretmesi.
- Runtime raporunun beklenen değerlerden doğrudan oluşturulması.
- Scene instantiate edilmeden test geçmiş gibi davranılması.

Asgari mutation kontrolü yap:
Fixture davranışını veya bağımsız beklentiyi kontrollü bozduğunda
gerçek pipeline başarısız olmalıdır.

Testi yeşile çevirmek için oracle'ı bozulan implementasyona uydurma.

## 8. ZAMANLAMA VE TEKRARLANABİLİRLİK

Senaryoyu wall-clock sleep'leriyle yönetme.
Sınırlı tick ve açık örnekleme noktaları kullan.

Şunları tanımla:

- Tick sıfırın anlamı.
- Eylemin tick içinde ne zaman uygulandığı.
- State'in eylemden önce mi sonra mı alındığı.
- Final state'in hangi tick tamamlandıktan sonra üretildiği.

Godot frame sinyalini beklemek ile o frame'deki bütün oyun güncellemelerinin
tamamlanmış olması arasındaki ayrımı doğrula.

Fixture için basit, sıralı ve mümkünse integer tabanlı durum kullan.
Gereksiz fizik simülasyonu veya kayan nokta karmaşıklığı ekleme.

Aynı koşullarda en az üç gerçek çalıştırmada aynı semantik state'i doğrula.
Timestamp, çalışma yolu ve execution ID'nin aynı olmasını bekleme.

Genel Godot fiziğinin platformlar/sürümler arasında bit düzeyinde
deterministik olduğunu iddia etme.

Headless koşu süresini mobil FPS veya GPU performansı diye sunma.

## 12. EXECUTION RAPORU VE ARTIFACT'LAR

Mevcut artifact/evidence modelini genişlet; paralel kayıt sistemi oluşturma.

Her ilgili attempt için mümkün olduğunca şunları sakla:

- Redakte edilmiş yürütme isteği.
- Kaynak/staging manifest'i.
- Godot executable ve version bilgisi.
- Harness version/hash.
- Import stdout/stderr ve process sonucu.
- Runtime stdout/stderr ve process sonucu.
- Gözlenen state raporu.
- Python validation raporu.

Süreç metadata'sı şunları kapsasın:

- workflow/task/execution kimlikleri
- attempt numarası
- executable, argv ve cwd
- başlangıç/bitiş bilgisi
- duration
- exit code
- timeout/termination durumu
- çıktı sınırı veya truncation bilgisi

Secret redaction ve bounded output kurallarını koru.
Godot loglarının ana CLI JSON stdout'una karışmasını engelle.

Rapor formatı en az şunları içersin:

- schema_version
- yürütme korelasyon kimliği
- scenario kimliği/fingerprint'i
- tamamlanan tick bilgisi
- istenen snapshot'lar
- terminal completion marker
- varsa yapılandırılmış hata

Yürütme kimliklerini engine değil Factory oluşturmalı.

Raporu önce geçici dosyaya yazıp kapat, ardından tamamlanmış çıktı olarak yayımla.
Kısmi dosyayı geçerli rapor sayma.

Engine'in bildirdiği hash veya dosya yoluna güvenme.
Dosya sınırını, boyutunu ve hash'ini Python tarafında doğrula.

## 15. HATA, TIMEOUT VE RECOVERY

Şu durumlar açıkça ele alınmalı:

- Godot bulunamıyor veya çalıştırılamıyor.
- Gerekli CLI capability desteklenmiyor.
- Import başarısız.
- Scene bulunamıyor veya parse edilemiyor.
- Harness sözleşmesi sağlanmıyor.
- Runtime nonzero exit.
- Timeout.
- Rapor yok, bozuk veya yanlış execution'a ait.
- Artifact yazımı başarısız.
- Output limiti aşılıyor.
- Orchestrator süreç çalışırken kapanıyor.

Parent tarafında import ve runtime için ayrı wall-clock timeout uygula.
Harness tick sınırını ikinci savunma olarak kullan.

Süreç sonlandırma ve process-tree yönetiminde mevcut ProcessRunner'ı kullan.
Kontrolsüz yeni subprocess yolu ekleme.

Orchestrator öldüğünde workflow kilidinin düşmesi,
Godot child process'inin de öldüğünü kanıtlamaz.

Recovery bunu dikkate almalı:
Önceki sahip olunan süreç durumu güvenle belirlenemiyorsa
ikinci bir kopyayı başlatmak yerine açıkça blokla.

PID tek başına güvenilir sahiplik kanıtı değildir.
Kullanıcıya ait başka süreçleri yanlışlıkla öldürme.

Retry yeni execution attempt üretmeli.
Eski loglar ve başarısızlık kanıtı korunmalı.

Tamamlanmış workflow üzerinde resume, Godot'u tekrar başlatmamalı.

Yeni run isteği ise yeni bir doğrulama koşusu olabilir;
bunu duplicate resume davranışından ayır.

## 16. ESKİ VE SAHTE KANITLARI REDDET

Aşağıdaki senaryolar için regresyon testi yaz:

- Önceki attempt raporunun yeni attempt'e taşınması.
- Doğru scenario ID ama yanlış execution ID.
- Rapor tamamlandı demesine rağmen eksik snapshot.
- PASS yazısı olmasına rağmen nonzero process exit.
- Exit code 0 ama rapor yok.
- State dosyasının validation öncesi değiştirilmesi.
- Raporun kendi expected/actual çiftini başarılı ilan etmesi.
- Rapor yolunun yönetilen alan dışına çıkması.

Başarı yalnız mevcut attempt'in doğrulanmış gözlemlerinden hesaplanmalı.

Bu önlemleri kötü niyetli yerel oyun koduna karşı kriptografik
kanıtlama veya sandbox güvenliği olarak pazarlama.

Amaç stale/malformed/yanlış bağlanmış kanıtları engellemektir.

## 17. TEST PLANI

Yeni birim testleri:

- Senaryo şeması ve sınırları.
- Allowlist action doğrulaması.
- CLI argument-array üretimi.
- Gözlem raporu şeması.
- Execution/scenario eşleşmesi.
- Assertion değerlendirmesi.
- Gate koşulları.
- Path ve output sınırları.

Godot gerektirmeyen entegrasyon testleri:

- Kontrollü fake ProcessRunner sonuçları.
- Import failure → runtime çağrı sayısı 0.
- Timeout ve nonzero exit.
- Malformed/missing/stale report.
- Approval öncesi process çağrı sayısı 0.
- Approval sonrası devam.
- Tamamlanmış resume → ek çağrı 0.
- Retry → yeni attempt ve korunan tarihçe.
- Hata durumunda artifact kaydı.

Gerçek Godot testleri:

- Temiz staging import.
- Gerçek scene instantiate.
- Tick tabanlı davranış.
- Beklenen state ve gate PASS.
- Bilerek yanlış assertion → FAIL.
- Script/scene hatası → FAIL.
- Kontrollü timeout → FAIL.
- En az üç koşuda semantik tekrar edilebilirlik.

Fake test ile gerçek engine testini ayrı etiketle.

Godot kurulu değilse normal core suite açık neden ile skip edebilir.

## 18. GERÇEK UÇTAN UCA KABUL

Kontrollü fixture kopyası üzerinde gerçek CLI komutlarını ayrı süreçlerde çalıştır.

Pozitif akış:

doctor
→ init
→ godot-verify
→ import
→ gerçek senaryo
→ state/log artifact
→ bağımsız validation
→ gate PASS
→ COMPLETED
→ inspect/artifacts.

Negatif akış:

Gerçek scene çalışır
→ bilerek yanlış beklenti
→ validation FAIL
→ workflow başarıya dönüşmez
→ expected/actual ve loglar inspect ile görülür.

Onay akışı:

Process izni onay gerektirir
→ BLOCKED
→ Godot import/runtime çağrısı 0
→ yeni süreçte approve
→ resume
→ gerçek çalıştırma
→ tamamlanma.

Recovery akışı:

Kontrollü kesinti
→ kalıcı kayıtlar
→ yeni CLI süreci
→ güvenli recovery/retry
→ eski attempt korunur
→ stale rapor kullanılmaz.

Süreç ortasında crash testi için yalnız test kapsamındaki kontrollü fault injection kullan.
Üretim CLI'ına gereksiz debug komutları ekleme.

Factory bağımsızlığı:

Fixture'ın Factory state ve harness içermeyen ayrı kopyasını
normal Godot ile çalıştır.
Oyun kodunun Factory import/autoload bağımlılığı olmadığını göster.
